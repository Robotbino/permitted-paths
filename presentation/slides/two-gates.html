Part 4 · control 3 · the gates

Two gates around each tool call

the agent loop

in words

while the task is not complete:
    proposal = the model suggests a tool call
    # GATE 1: is the shape of the call correct?
    result = the tool makes a result,
             with no change to data
    # GATE 2: does the result obey the ontology?
    record the change,
    or send the cause back to the model

Gate 1 · input

Before the tool operates. The shape of the call: types, ranges, necessary fields. It reads only the call.

Gate 2 · output

After the tool operates. The sense of the result: cardinality, roles, agreement with the state of the world.

The rule · a pure agent

The agent calculates and gives a result. It does not change the world during the loop. Thus you can reject a result and lose nothing.

GE 04 · from a source: Frank Coyle

PART 4

The third item is the important one. If the agent changes no data during the loop, you can reject a result and lose nothing. Do the Gate 2 check and the commit in one transaction, and add a unique constraint in the database for each cardinality rule. A unique constraint on “an order has at most one refund” would have stopped the bug on slide two, at the database, with no model involved at all.
