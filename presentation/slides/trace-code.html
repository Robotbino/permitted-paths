The trace: one row for each step

the row

written by the runtime

trace.write({
  "run_id":     run_id,
  "step":       step,
  "node":       node,
  "kind":       kind,
  "inputs":     redact(before),
  "output":     redact(after),
  "tool_calls": calls,
  "gate":       verdict.gate,     # GATE 1, GATE 2
  "rule":       verdict.rule_id,  # LV-1, LV-3
  "result":     verdict.name,     # PASS or FAIL
  "model":      model_id,
  "latency_ms": ms,
})

the query

which rule gives FAIL most?

SELECT rule, count(*) AS fails
  FROM trace
 WHERE result = 'FAIL'
   AND ts > now() - interval '7 days'
 GROUP BY rule ORDER BY fails DESC;

Record the gate and the rule

The three amber fields make the query possible. With no rule id, you have a log that you cannot count.

PART 5

This slide is the loop closing: the ontology checks the run, the run writes a trace, and the trace tells you which part of the ontology to change. A rule that fires constantly is either a bad rule or a missing fact. A rule that never fires may be dead. A node whose attempts are always two is a prompt worth rewriting. Without the rule id in the row, none of that is possible and you are back to reading logs by hand.
