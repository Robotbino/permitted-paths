The trace is one row per step, and it is what makes the next run better

trace.write({
    "run_id":    run_id,      "step":     step,
    "node":      node,        "kind":     kind,
    "inputs":    redact(before), "output":   redact(after),
    "tool_calls": calls,
    "gate":      verdict.gate,  # GATE 1, GATE 2 or None
    "rule":      verdict.rule_id, # LV-1, LV-3 …
    "result":    verdict.name,    # PASS or FAIL
    "model":     model_id,    "latency_ms": ms,
})

-- which rule rejects most often? that is the next thing to fix
SELECT rule, count(*) AS fails
  FROM trace
 WHERE result = 'FAIL'
  AND  ts > now() - interval '7 days'
 GROUP BY rule ORDER BY fails DESC;

Record the gate, not only the answer

A trace that holds the rule id turns the intelligence plane into something you can query. Without it, you have logs.

Read it three ways

A rule that fires constantly is either a bad rule or a missing fact. A rule that never fires may be dead. A node whose attempts are always two is a prompt worth rewriting.

Redact on the way in

The trace holds requests and results. Decide what it may keep before you write the first row, not after the first audit.

This slide is the loop closing: the ontology checks the run, the run writes a trace, and the trace tells you which part of the ontology to change. Without the rule id in the row, none of that is possible and you are back to reading logs by hand.
