An ontology you can run

class OrderStatus(str, Enum):      # the permitted answers, not prose
    PENDING   = "PENDING"
    PAID      = "PAID"
    FULFILLED = "FULFILLED"
    REFUNDED  = "REFUNDED"
    CANCELLED = "CANCELLED"

RULES = [  # data, so a person can read them and a test can run them
  Rule("LV-1", "an order has at most one refund",
       lambda f, r: count(f, "refund", order_id=r.order_id) <= 1),
  Rule("LV-2", "a refund pays the customer of its order",
       lambda f, r: r.customer_id == order(f, r.order_id).customer_id),
  Rule("LV-3", "only a PAID or FULFILLED order can be refunded",
       lambda f, r: order(f, r.order_id).status in REFUNDABLE),
]

What changed

The prompt sentence “never refund an order twice” became LV-1. A sentence is advice. A rule with an id is something a gate runs, a test asserts and a trace can name when it fails.

Start with the enumeration

Five permitted values end the argument about order status from part 1. Four of those five answers are now not merely unlikely — they do not exist.

Give every rule an id

The id is what the rejection carries, what the trace records and what you count later to find the rule that fires most.

Control 2 · GE 04

Keep the rules as data rather than scattered if-statements. Data can be listed in a review, diffed in a pull request, and counted in the trace table. That is what lets the ontology improve from evidence instead of from opinion.
