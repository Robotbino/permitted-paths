The order to build it in

Each step is useful on its own, and each one pays for the next. Do not start with the graph.

WhenWhat you buildHow you know it worked
Hour 1Find one rule in one prompt. Make it an enumeration and a validator.Measure the variation before and after with the five-runs procedure from part 1.
Day 1Gate 1 on every tool: a schema per call, extra fields forbidden, readable rejections.Malformed calls stop reaching your tools. Count them for a week.
Week 1Make the agent pure, then add Gate 2 and the matching database constraints.A rejected result costs a rollback and nothing else.
Week 2Write the trace: one row per step, with the node, the gate, the rule id and PASS or FAIL.You can answer “which rule fails most?” with a query, not a guess.
Week 3Only now, the execution graph: pull the sequence out of the loop into NODES and EDGES.The edge functions have unit tests that run with no model.
Month 2Feed the trace back: fix the rules that fire most, add the facts that were missing.The same task needs fewer attempts than it did last month.

If you only ever do hour one, you have still moved one decision from the model to the system. That is the course.

Controls 2 and 3 first; control 1 last

Say the ordering out loud, because it is the opposite of what people expect. Gates and ontologies are cheap, local and useful on day one. The graph is the biggest change and the one most likely to be rebuilt, so it comes after you have traces that show where the run actually goes.
