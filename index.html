The claim

Put the structure outside the model. Then the model makes a smaller number of decisions, and the system makes the other decisions.

GE 00 Session GuideThe start page of the course

You stopped in a later part. Continue where you stopped.

An agent gets a small task: “Add a refund button to the order page.” It writes an endpoint, and the endpoint operates. Then a customer clicks the button two times, and gets two refunds. No sentence in the prompt stopped it.

You give the same task again, and the agent makes a different design. The agent did not become worse between the two runs. An agent is a language model that uses tools in a loop. The model is probabilistic. Thus the same task can give different results.

You cannot remove the probability from the model. But you can put structure around the model. The structure makes the decisions that must not change. Graph Engineering is the design of the graph in which an agent system operates.

Three controls

Three controls decrease the variation. Each part of this course uses them.

1A smaller number of decisions for the modelExecution graph2
2A smaller number of permitted resultsOntology and schema4
3A check before a result causes a changeGate and verifier2, 4

The intelligence plane keeps the knowledge that the three controls use. It also uses the evidence of each run to make the controls better. That is part 5.

How this course operates

This course is an execution graph, and you are a run.

  • Each part is a node. The path on the left edge of the page shows the nodes and where you are.
  • Each part ends with a gate. The gate gives PASS or FAIL and the cause. Each question has a maximum of two attempts. The first FAIL gives a hint and a link back to the section. At the maximum, the gate escalates: it stops and gives you the worked answer.
  • The course records a trace of your run in this browser. In part 8, you see your own trace as a context graph.
  • One difference: this course does not stop you at a gate with a FAIL result. It records the result and shows you the way back. A gate in a real system stops the result before it causes a change.

One small experiment connects the parts. In part 1, you ask a model five times for the status of order 1042. In part 4, you put your five results into a validator. In part 6, a gate in a factory stops a status that is not permitted.

Why the instruments work this way

The design of the instruments comes from research on learning. Each item below changes what you do on the page.

  • Estimate first. Some instruments ask for an estimate before the explanation. A wrong estimate is expected. In experiments, people who tried to answer before they studied remembered more afterwards, even when their first answer was wrong richland.
  • Worked examples, then fewer hints. Before you classify items yourself, some items are already solved, with the reason. For beginners, studying solved examples helped more than solving problems alone sweller-cooper. The help then decreases as you continue renkl-atkinson. Hints are optional, because help that is good for a beginner can slow down a person who already knows the idea kalyuga.
  • Can you say why? After a correct answer, you select the reason. Students who explained examples to themselves learned more from them chi. That study compared students; it did not assign the method at random, so treat it as good evidence, not proof.
  • Gates. A gate asks you to retrieve the idea. In the original experiments, a test after study gave better memory a week later than a second reading roediger-karpicke.

The same question, five answers

Why does the output of an agent change, and what decreases the variation?

GE 01 §1–5Session plan of the notes: 12 minutes of 100, or 8 of 60. With the instruments, more time is necessary.

Start with an experiment. Order 1042 has an accepted payment. The email with the game key is in the send queue. Ask a model for the status of the order, five times, each time in a new chat.

A model gives a probability

A language model calculates a probability for each possible next token. Then it selects one token. It does this again for each token of the result. Thus the same input can give a different output.

A developer frequently asks: “Why not set the temperature to zero?” A low temperature decreases the variation. It does not remove the variation from a full system. There are three answers:

  • A hosted model can give a different output with temperature zero. One measured cause: the server groups requests in batches, and the size of the batch changes with load, which changes the arithmetic he-nondeterminism. A study of code generation found that temperature zero did not make the output deterministic ouyang-nondeterminism. The supplier can also change the model.
  • One different token at the start of a loop changes each step that comes after it.
  • The tool results change between two runs, because the files and the data change.
Key idea

You cannot be sure that the model gives the same output each time. You can make the system around the model predictable.

An agent makes many decisions

In each turn of the loop, the model makes decisions. Each decision is a point where the result can change.

Decision that the model makesExample of an incorrect result
Which step is nextThe agent writes code before it reads the repository
Which tool to useThe agent does a search of the web, but the answer is in the database
Which arguments to sendThe agent sends the incorrect order number
What a term meansTwo agents use two definitions of “active customer”
Which value is permittedThe agent writes the status “probably shipped”
When to stopThe agent stops too soon, or it does not stop
If the work is goodThe agent gives approval to its own work

A paragraph of instructions in a prompt does not reliably prevent these results. The model does not always obey an instruction.

The effect of small errors increases

Look at a task with a sequence of steps. Each step must be correct for the task to be correct. Before you read the calculation, do the experiment.

If each step is correct with probability p, then n steps are all correct with probability p^n.

Correct rate of one step5 steps10 steps20 steps
99%95%90%82%
95%77%60%36%
90%59%35%12%

Teaching model This calculation is correct only if the steps are independent and each has the same rate. In a real agent, errors are often connected: one wrong fact can cause many wrong steps. Also, a verifier can find and correct a wrong step. Thus a real rate can be better or worse than the table. Use the table for the direction of the effect, not for a number.

The table gives two lessons:

  • A long sequence of model decisions is not reliable, although each decision is good.
  • If you remove decisions from the sequence, the full task becomes more reliable.

What “deterministic” means here

The word “deterministic” can cause confusion. These notes use it for the system, not for the model.

The aim is a system that gives the same permitted paths, the same checks, and the same permitted values on each run.

How to measure the variation

  1. Do the same task ten times with the same input.
  2. Record the path of each run.
  3. Record the value of each typed field of each run.
  4. Count the different paths and the different values.
  5. Add one structure, then do steps 1 to 4 again.
  6. Compare the two sets of numbers.

A smaller count shows that the system is more predictable. This measurement is about variation. It is not a measurement of quality. You will do this procedure in part 2.

Take decisions away from the model

Control 1. What does an execution graph remove, and when is a graph necessary?

GE 02 §1–3, 7, 8Session plan of the notes: 20 minutes of 100, or 12 of 60. With the instruments, more time is necessary.

An agent gets a change request. It must classify the request, write a plan, get approval, write the change and do the tests. First, see the task as one loop. Then move the decisions out of the model, one at a time.

Definition

Graph Engineering is the design of the graph in which an agent system operates. These notes use the name execution graph for that graph.

  • A node does one unit of work.
  • An edge selects the next node.
  • The state is the data that moves from node to node.

You can think of the graph as a state machine. The idea is not new. Workflow engines used it for many years. A model in a node is also not new. The LangChain article says that the new part is a full agent in a node.

Key idea

In a loop, the model selects its own path. In a graph, you select the permitted paths. The model reasons in a node, or it selects one permitted path.

The four parts

Nodes

A node is not always a model call. Give each node one responsibility.

Type of nodeWhat it containsPredictable?
Fixed stepCode. No model.Fully
Model stepOne model call with no toolsNot fully
Agent stepA model that uses tools in a loopLess than a model step
VerifierA check of the work of a different nodeFully, if it is code
Person stepA person gives approval or rejectsFully, as a point in the path

A test for a node. Write what the node does in one sentence with no “and”. If you cannot do this, divide the node.

Edges

Type of edgeWho selects the next node
Fixed edgeNo one. Node B always comes after node A.
Conditional edge, by codeA function reads the state and gives the name of the next node.
Conditional edge, by modelA model reads the state and selects one of the permitted next nodes.
Fan-outOne node starts two or more nodes at the same time.
Fan-inParallel branches connect again at one node.

Put the stop rules on the edges. The maximum number of attempts is a decision about the path. It is not a decision about the content.

State

The state is one object. Each node reads the state and writes to the state. The state is a contract between the nodes.

  • Give each field a type.
  • Give each field one owner. Only the owner writes the field.
  • If parallel branches write the same field, write a merge rule for that field.

Control

A graph can operate for a long time. Failures during a run are usual.

  • Checkpoint: record the state at the end of each node. Then a run can continue after a failure.
  • Budget: set a maximum cost for each node and for the full run.
  • Terminal node: give the nodes where the run stops.

After a failure, the node starts again from its first line. Thus make each node safe to do two times. This is most important for a node that opens a pull request or sends a payment.

Watch one run

From a source Two results in the sources show that structure can increase the quality of a result. They do not measure the variation between runs. When to use a graph

The default is one loop with a strict verifier. When a specific problem occurs, add a graph. One clear “yes” in the right column is sufficient.

Question about the taskOne loop is sufficientUse a graph
Can you write the task as one instruction?YesNo. The task goes from one role to a different role.
Does each step use the same model and tools?YesNo. Some steps use a small model, some use a large model.
Are some steps independent?NoYes, and they can operate at the same time
Who makes the decision that the result is good?A check in the loop, for example the testsA node that did not write the result
What must occur after a failure of one step?Try againIsolate the failure. The other work continues.
Who must read the record of the path?Only your teamA person outside the team must see which step occurred, and why

Three good causes for a new node: specialization (the node uses a different model or different tools), parallel work (the branches are independent, and the decrease in time is important to a person) and independent verification (a node that did not write the work examines the work).

When not to use a graph

  • The task is open. You cannot give its steps before the run. An example is general research. Use an agent harness for such a task. The harness is the code around the model: the tools, the memory, the skills and the files.
  • All the steps are code. Then a script is sufficient.
  • Do not divide the work between parallel agents if all the agents use the same context.
  • Do not divide the work between parallel agents if each subtask must have the results of the other subtasks.

From a source The last two items are advice from Anthropic for systems with many agents. The PuppyGraph guide gives this advice.

A code example with LangGraph Reference · GE 02 §10

call_model, run_checks and notify_person are placeholders. run_checks gives a list of problems. See how each field has an owner, and how the stop rule is on the edge.

from typing import Literal, TypedDict
from langgraph.graph import END, START, StateGraph

MAX_ATTEMPTS = 2

class ChangeState(TypedDict):
    request: str                       # owner: the caller
    draft: str                         # owner: writer
    attempts: int                      # owner: writer
    verdict: Literal["pass", "fail"]   # owner: verifier
    problems: list[str]                # owner: verifier

def writer(state: ChangeState) -> dict:
    feedback = state.get("problems", [])              # empty on the first attempt
    draft = call_model(state["request"], feedback)    # model step
    return {"draft": draft, "attempts": state.get("attempts", 0) + 1}

def verifier(state: ChangeState) -> dict:
    problems = run_checks(state["draft"])             # fixed step: code
    return {"verdict": "fail" if problems else "pass", "problems": problems}

def escalate(state: ChangeState) -> dict:
    notify_person(state["request"], state["problems"])  # person step
    return {}

def route(state: ChangeState) -> Literal["writer", "escalate", "__end__"]:
    # The stop rule is on the edge, not in a prompt.
    if state["verdict"] == "pass":
        return END
    if state["attempts"] >= MAX_ATTEMPTS:             # the writer ran MAX_ATTEMPTS times
        return "escalate"
    return "writer"

builder = StateGraph(ChangeState)
builder.add_node("writer", writer)
builder.add_node("verifier", verifier)
builder.add_node("escalate", escalate)
builder.add_edge(START, "writer")
builder.add_edge("writer", "verifier")
builder.add_conditional_edges(
    "verifier", route, {"writer": "writer", "escalate": "escalate", END: END}
)
builder.add_edge("escalate", END)
graph = builder.compile()

result = graph.invoke({"request": "Add a refund button"})

Four things with the name “graph”

The word “graph” has more than one meaning. Which graph do you mean?

GE 03 §1, 2, 5Session plan of the notes: 5 minutes of 100, or 2 of 60. With the instruments, more time is necessary.

An agent gives or refuses a loan. That one case has four different graphs in it. Look at the same case through four lenses.

The four types

TypeQuestionNodes areLife
Execution graphWhat comes next?Units of workThe design is permanent. Each run is one pass through it.
Knowledge graphWhat is in the domain?Entities, for example a customer or a fileContinues across runs
Context graphWhat occurred in this run?Steps, tool calls, the records that the run usedPermanent. Each run adds a trace.

Summary by the notes The Neo4j talk gives three types: execution, context and procedural. The notes add the knowledge graph from the PuppyGraph guide as a fourth type. The Life column is a summary by the notes.

The execution graph and the procedural graph are about control. The knowledge graph and the context graph are about data. A procedural graph is data that a harness loads. An execution graph is code that the runtime enforces.

Two possible causes of confusion. GraphRAG and knowledge graphs are about data. Graph Engineering, in its narrow sense, is about control. A context graph is a graph of traces. It is not the context window of a model.

How the four types connect

A skill with the shape of a graph

A skill is a text file with instructions for one type of task. The agent reads a paragraph and selects an action. That decision is probabilistic. You can compile the skill into a graph:

  • Each decision point becomes a node.
  • Each instruction that code can do becomes a script.
  • The model gets only the decisions for which judgment is necessary.

The loan example

From a source The talk by Zachary Blumenfeld shows an agent that gives or refuses a loan. The first version had the data graph and written instructions. The agent did the same review two times. One run found an older case, thus the two paths were different. The trace showed the cause of the difference only after the run.

An instruction to escalate when the agent is not sure gave that decision to the model. The model did not have calibrated confidence values. The second version is a procedural graph. The scripts use the policy rules first. The model makes a decision only when the rules give no decision.

The talk gives these results for the demonstration:

  • With the procedure, the same model used approximately half the time. The model did not change. Only the structure changed.
  • With the paths in scripts, the team used a smaller model for the other work. This decreased the time and the cost more.
  • The first version was also correct almost each time.

These numbers come from a small number of demonstration runs. They are not a benchmark. The maximum on the report cycle is an addition by the notes.

Three gains

GainMeaning

Keep the permitted paths and the actual paths together. Then you can answer two questions: Which rule or which model made the decision in this case? Which branch of the procedure did no run use?

Execution graph and knowledge graph Reference · GE 03 §3

The two graphs meet at one point: a node that reads data. The execution graph selects when a node reads data. It cannot tell you if the query has a correct meaning. A query can give rows and be incorrect.

For example, the query can use a relation that is not in the business. The node gets rows. The edge sends the rows to the next node. The next node reasons about an incorrect result.

The PuppyGraph guide suggests one shared specification of the domain below all the nodes. PuppyGraph sells such a layer. This specification is an ontology (part 4).

Context graph: the trace of a decision Reference · GE 03 §4

A context graph keeps three types of memory together: the conversation; the entities in the conversation and in the records; and the decision trace, which is the steps and the tool calls of the run.

With these relations, a reviewer can start at a question and find the run. Then the reviewer can go from one step back to the record that the step used. A trace shows the cause of a decision only after the run. It does not control the next run. For control, a procedural graph is necessary.

Vectors and graphs together Reference · GE 03 §6

A vector search finds text with almost the same meaning. A graph query goes along the relations between entities. The Neo4j article connects the two methods: a vector search finds related text; the document identifiers select a part of the graph; the model writes graph queries for that part only.

MethodStrong pointWeak point in the article
Vector searchFinds related text quicklyFrequently does not find how the facts connect
Graph that a model makesShows the relations between entitiesCan be inconsistent and difficult to query

The article compares two ways to make a knowledge graph. If the model extracts all entities and relations, the number of node types and relation types can increase with no control. If the metadata of the data set gives the types, the number of types stays small. The article gives more useful queries as the result of one demonstration. It gives no measurement. The second way is possible only for a data set with good metadata.

Key idea

Constraints on the types can increase the number of useful queries. A smaller number of types gives a smaller number of queries that have no relation to the question.

Say what is permitted

Controls 2 and 3. An ontology gives the permitted results. A gate rejects each other result.

GE 04 §1, 5, 7, 10Session plan of the notes: 18 minutes of 100, or 12 of 60. With the instruments, more time is necessary.

In part 1, you asked for the status of order 1042 five times. The correct status is PAID. How many of your five results can a system use?

Definition

An ontology is a formal specification of a domain. All parts of a system share this specification. It contains four things:

PartExample
Types of things (classes)Customer, Order, Product, Refund
PropertiesAn order has a status and a total
RelationsA customer places an order
Constraints and rulesAn order can have only one refund

A person and a machine can read an ontology. That is the difference between an ontology and a paragraph in a prompt.

TermMeaning
TaxonomyA tree of types. It has only the relation “is a type of”.
SchemaThe structure of data in one database or one message
OntologyThe types, relations and rules of a domain. It is independent of one database.
Knowledge graphThe facts about real things. The facts obey the ontology.

The two gates

From a source Frank Coyle puts two gates around each tool call in the agent loop.

while the task is not complete:
    proposal = the model suggests a tool call
    # GATE 1: is the shape of the call correct?
    result = the tool makes a result, with no change to data
    # GATE 2: does the result obey the ontology?
    record the change, or send the cause back to the model
GateWhenWhat it examinesTool
Gate 1: inputBefore the tool operatesThe shape of the call: types, ranges, necessary fieldsPydantic
Gate 2: outputAfter the tool operatesThe sense of the result: cardinality, roles, agreement with the state of the worldThe ontology
The ruleDuring the loopThe agent calculates and gives a result. It does not change the world.A pure agent

Gate 1 reads only the call. Gate 2 reads the call, the result, the ontology and the current facts.

The third row is important. If the agent does not change data during the loop, you can reject a result and lose nothing. Do the Gate 2 check and the commit in one transaction. Add a unique constraint in the database for each cardinality rule.

Where an ontology decreases the variation

An ontology can act at three points. Only the second and the third are constraints.

PointWhat occursIs it a constraint?
Before the model callThe model sees the permitted values in its contextNo. This is help for the model.

When a gate rejects a result, the cost is one more model call.

Five mechanisms

#MechanismEffect
1Closed vocabularyA value that is not in the list does not go to the next step

A sixth effect is feedback. When a gate rejects a result and gives the cause, the model knows what to correct.

Key idea

A prompt asks the model to obey a rule. An ontology makes the rule a check for each result.

Inference and constraints

A graph with names is useful. A graph with rules is more useful. Three W3C standards add the rules: RDFS w3c-rdfs, OWL w3c-owl and SHACL w3c-shacl. RDF is not necessary at the start. An enumeration in code and a small validator function are sufficient for a first version. But the three standards do different things with data that does not obey a rule. Make a prediction below.

Procedure: make your first ontology

  1. Write the ten most important nouns of the domain.
  2. For each noun, write its properties and their types.
  3. Write the relations between the nouns as “subject, verb, object”.
  4. For each field with a fixed list of values, write the list.
  5. For each relation, write the cardinality: one, or many.
  6. Write the three errors with the highest cost. Write one rule for each error.
  7. Put the lists and rules in code: enumerations, a schema, a validator function.
  8. Use the validator at Gate 2, before each change to data.
  9. When a new type of error occurs, add a rule.

class RefundCall(BaseModel):                          # Gate 1: the shape of the input
    model_config = ConfigDict(extra="forbid", strict=True)
    order_id: PositiveInt
    amount_cents: PositiveInt
    payee_id: PositiveInt
    new_status: str

ALLOWED_STATUS = {"PAID", "SHIPPED", "REFUNDED"}      # from the ontology

def ontology_check(order, proposed) -> list[str]:     # Gate 2: the sense of the result
    problems = []
    if proposed.status not in ALLOWED_STATUS:
        problems.append(f"Status {proposed.status} is not in the ontology.")
    if order.refund_count >= 1:
        problems.append("An order can have only one refund.")
    if proposed.payee_id != order.customer_id:
        problems.append("The payee must be the customer who placed the order.")
    return problems

def handle(model_proposal) -> None:
    try:
        call = RefundCall.model_validate(model_proposal)
    except ValidationError as error:
        send_back_to_model([str(error)])              # Gate 1 rejects and gives the cause
        return
    proposed = plan_refund(call)                      # pure: no write to the database
    with transaction():                               # the check and the commit are one unit
        order = load_order_for_update(call.order_id)  # lock the order
        problems = ontology_check(order, proposed)
        if not problems:
            commit(proposed)                          # the only step with a side effect
    if problems:
        send_back_to_model(problems)                  # or escalate to a person

A fixed list of values is part of the ontology. Gate 1 can also use that list, if you make the schema from the ontology. Keep the list in one location only.

One ontology below all the nodes Reference · GE 04 §6

In a graph, many nodes read data. If each node has its own specification of the data, the specifications become different. The PuppyGraph guide gives two results of one enforced ontology: all the nodes use one contract, and a rejected query is a signal. An edge can use that signal to send the work back.

Ontology Engineering: the next level Reference · GE 04 §8

The survey paper gives Ontology Engineering as the future direction after Graph Engineering. A graph makes the relations explicit. But the agents can disagree about the meaning of terms. What is “task complete”? What is sufficient evidence? Which action has authorization?

An ontology for an agent system gives these shared concepts: goals, agents, capabilities, evidence, policies, states and outcomes. Ontology Engineering gives the shared specification. Graph Engineering makes structures for one task. The runtime enforces the rules.

The paper recommends a hybrid method for changes to the ontology: a model suggests a change and gives its cause; reasoners, validators, tests, version control and people accept or reject the change.

Limits Reference · GE 04 §9
  • An ontology gives consistent meaning. It does not make a fact correct. Connect each fact to a source.
  • An ontology has a maintenance cost. The domain changes, and the ontology must change with it.
  • A large ontology is not better. Include only the concepts that are necessary for a decision.
  • Rules that are too strict stop valid work. Start with the rules that prevent the errors with the highest cost.

What the system knows

The three controls get their rules and their facts from one layer. Where does the knowledge live?

GE 05 §2, 3, 6, 10Session plan of the notes: 10 minutes of 100, or 5 of 60. With the instruments, more time is necessary.

All teams can buy access to the same models. Thus the model is not the difference between two agent systems. The difference is what each system knows about its own domain.

From a source Richmond Alake gives a story from the Second World War in his talk. Two groups had the same intercepted messages. One group kept paper records of old messages for months. That group found that the letters “AF” meant Midway. The other group did not find this.

Measured The history is documented: US Navy code breakers thought that “AF” was Midway. To confirm it, Midway sent a false message that its water plant was damaged. A Japanese message then reported that “AF” was short of water nsa-midway. The talk uses the story as an analogy for memory. The story does not measure anything about agents.

Key idea

To have a message is not the same as to know its meaning. The recorded experience gives the meaning.

The planes

The word “plane” comes from network engineering. A plane is a layer of a system with one responsibility. The talk gives two planes: the control plane and the intelligence plane. The notes add the data plane as a name for the agent runtime. Teaching model The three planes are a way to sort the parts of a design. They are not a standard.

To find the plane of an item, ask one question: what does this item do in the system?

  • Data plane: it does the work. It acts during a run. Example: the model call that writes the plan.
  • Control plane: it sets limits. It permits, stops or counts what the agent does. Example: a person must give approval before the change.
  • Intelligence plane: it keeps knowledge. It holds what the system knows, also after the run ends. Example: the ontology with the permitted status values.

One pair is easy to confuse. Tool permissions say what the agent can do: a limit. Access to data says what the agent can know: knowledge.

The control plane and the intelligence plane do different work:

  • The control plane sets limits for the agent.
  • The intelligence plane influences which decision the agent makes in those limits.

A software factory is a workflow that you can do again and again to make software. Agents do the steps for which judgment is necessary. Code does the other steps.

The factory in this part gets a change request. It gives a change that has test results and a review. The application is a game store with a catalog, a cart, orders, payments and refunds. The factory must give these results on each run:

A small real one

The three controls on a real project: a small intelligence plane that one developer made with Markdown files.

This part shows a pattern from a real project: the maintenance of a legacy application. It shows only the structure. It contains no business rules, no names and no code from that project. The examples use the game store of part 6.

The application is a legacy enterprise web application. It has a workflow engine, many pages and many business rules. The documents and the code do not always agree.

On such an application, an agent with no structure has these problems:

  • It gives different answers to the same question about a rule.
  • At the end of each agent session, it loses what it learned.
  • It cannot see the difference between a verified fact and a claim with no evidence.
  • It reads too much code to find one rule.

The solution: one note for each claim

The agent reads the note first. Then the note points to the source code.

The agent session loop

Each agent session has the same five steps. This loop is a small execution graph.

There is one skill for each type of task: a question about a rule (answer from the graph, with the evidence); “Is this requirement in the code?” (an audit of one requirement against the code); a new feature or a change (a plan with the related rules); a defect from a tester (correct the defect and add the lesson); and the end of an agent session (closeout). A skill is procedural memory.

The checks

Scripts do most of the checks. A model does not do these checks. A script does a quick check of the notes and the code at the start of each agent session, and a full check each week. There are code lints for known failure patterns, knowledge lints for the graph, a change check, and the graph validator. Only the audit of one requirement is the work of an agent, with a skill.

With a baseline, the checks stay useful: they show only what changed.

Architecture A: what occurs when you send a task

  1. On the computer, in the folder of the repository, a session runs: claude --remote-control "employee-manager". It connects out to Anthropic and opens no port.
  2. You open the session in the Code tab of the Claude app and type the task.
  3. Claude Code works on your computer, with your files, your CLAUDE.md, your skills and your MCP servers. With --add-dir it can also read the vault.
  4. When it wants to run a command that no permission rule allows, the app shows a prompt and waits for you. A push notification tells you.
  5. You read the result and the diff in the app. You push from there, by a message, when you are ready.

For a repository on GitHub there is a second path: start a cloud session in the app. It clones the repository into a machine of Anthropic, works with your computer off, and pushes a branch.

QuestionAnswer for architecture A
Must the computer be on?For the local path, yes: on, awake, with the session process running. For a cloud session, no.
What occurs when it goes offline?Claude Code connects again when the computer returns. After about ten minutes with no network, the server mode ends. A stopped server session can be continued for about four hours.
Can it work with no intervention?Only inside the permission rules. Each other action waits for your answer. Cloud scheduled tasks run with no session, but in the cloud.
Which parts are native?All of them: Remote Control, cloud sessions, push notifications, worktrees, skills, subagents, hooks, MCP.
What needs more infrastructure?A message that starts work when no session is open; checks that do not depend on the agent; one record of all tasks; an approval in a chat.

Architecture A covers a large part of the list: a task from the phone, your project context, the agent, tests, progress, review and approval. It does not give you a path that starts with no open session, and it does not give you checks outside the agent. Those two are the reason for architecture B.

The Telegram channel. Claude Code has an official plugin that puts Telegram messages into a local session. It is a research preview, it needs Bun, and it receives messages only while the session is open. It is the shortest way to a chat interface. It is not an automation: no check, no record and no approval step are outside the session.

Architecture B: what n8n adds, and what it needs

n8n holds the path of the work as a graph of nodes. Each node is code with one job. The agent is one step in that path, and it gets only the tools of the mode. This is the design of parts 2 and 6, with real products.

  • It adds: an intake that listens when no session is open; identity checks before any agent starts; a fixed sequence of investigate, approve, change, test, approve, push; a stored history of each run; an approval with buttons in the chat.
  • It needs: a public HTTPS address, because the Telegram Trigger node of n8n uses a webhook; a bridge, because n8n has no official node for the Claude Code command line; and your computer on.
  • It does not add: intelligence. The workflow of this part contains no model call. The classification of a message is a table in a Code node.

Architecture C: what improves, and what you pay for it

Architecture C moves the intake to a small server that is always on. Your computer becomes a worker that asks for the next job, so it opens no port at all. Tasks wait in a queue while the computer is off, and for a repository on GitHub the server can start a cloud session through the API trigger.

The bridge

The bridge is one file of Node.js with no dependencies. It listens on 127.0.0.1 only. It has three addresses and no address that runs a command from the request.

AddressWhat it does
POST /tasksChecks the request, writes the job file, answers 202, starts the agent in a queue of one.
GET /tasks/<id>Gives the status and, when it is finished, the report, the test result and the diff summary.
POST /tasks/<id>/publishPushes the branch of a finished change. It refuses when its own test run did not give PASS, and when approved is not true.

Four decisions in the file matter more than the others:

  • The prompt goes in on stdin. The text from the phone is never part of a command line, so a message cannot add an argument or a second command. The process starts with no shell.
  • The tools come from the mode, not from the request. A request names a mode. The list of tools for that mode is a constant in the file. From Claude Code 2.1.302, a run with -p denies each tool call that no rule allows.
  • The bridge runs the tests. The agent can say “the tests pass”. The bridge does not read that sentence. It runs the command of the config and reads the exit code.
  • The API key is removed. The bridge deletes ANTHROPIC_API_KEY from the environment of the child process, so the run uses your plan.

//
// It is the only custom component of architecture B. It has no dependencies: Node.js 20 or later.
//   node server.mjs            starts it with ./config.json
//   node server.mjs --check    reads the config, prints the problems, and stops
//
// What it does, in this sequence:
//   1. Accepts POST /tasks on 127.0.0.1 only.
//   2. Runs five checks in code (validate). A request that fails one check never reaches the agent.
//   3. Starts `claude -p` in the folder of an allowlisted repository, with the tools of the mode only.
//      The prompt goes in on stdin, so the text from the phone is never part of a command line.
//   4. For mode "change": Claude Code works in its own git worktree. Then the bridge runs the tests
//      itself and reads the diff itself. It does not use the agent's statement about them.
//   5. Writes each step to jobs/<id>.json and to audit.log, and sends the result to the callback URL.
//
// It never pushes, never deploys, and has no endpoint that runs a command from the request.

function sameSecret(a, b) {
  const x = createHash('sha256').update(String(a)).digest(), y = createHash('sha256').update(String(b)).digest();
  return timingSafeEqual(x, y);
}

/** Gives null when the request is permitted, or { status, check, error }. The sequence is fixed. */
export function validate(req, token, config = cfg, secret = TOKEN) {
  if (!secret || !sameSecret(token || '', secret)) return { status: 401, check: 'token', error: 'The shared secret is missing or not correct.' };
  if (!config.users.includes(String(req.user_id))) return { status: 403, check: 'sender', error: 'The sender is not on the allowlist.' };
  const repo = config.repos[req.repo];
  if (!repo) return { status: 403, check: 'repo', error: 'The repository is not on the allowlist.' };
  if (!MODES[req.mode] || !repo.modes.includes(req.mode)) return { status: 403, check: 'mode', error: 'This repository does not permit this mode.' };
  if (NEEDS_APPROVAL.includes(req.mode) && req.approved !== true) return { status: 409, check: 'approval', error: 'This mode needs approval for this task.' };
  if (!ID.test(String(req.task_id || ''))) return { status: 400, check: 'shape', error: 'task_id must be 6 to 40 lower-case letters, digits or hyphens.' };
  if (typeof req.prompt !== 'string' || !req.prompt.trim() || req.prompt.length > 4000) return { status: 400, check: 'shape', error: 'prompt must be text of 1 to 4000 characters.' };
  if (req.callback_url && !String(req.callback_url).startsWith(config.callbackBase)) return { status: 400, check: 'shape', error: 'callback_url must start with the configured callbackBase.' };
  return null;
}

/** Starts a program with no shell. Gives { code, out, err, timedOut }. */
function run(command, args, { cwd, input, minutes = 5, env = process.env } = {}) {
  return new Promise((done) => {
    const child = spawn(command, args, { cwd, env, shell: false, windowsHide: true });
    let out = '', err = '', timedOut = false;
    const timer = setTimeout(() => { timedOut = true; child.kill(); }, minutes * 60_000);
    child.stdout.on('data', (d) => { if (out.length < 2_000_000) out += d; });
    child.stderr.on('data', (d) => { if (err.length < 200_000) err += d; });
    child.on('error', (e) => { clearTimeout(timer); done({ code: -1, out, err: String(e), timedOut }); });
    child.on('close', (code) => { clearTimeout(timer); done({ code, out, err, timedOut }); });
    if (input != null) child.stdin.end(input); else child.stdin.end();
  });
}

function claudeArgs(job, repo) {
  const mode = MODES[job.mode];
  const args = ['-p', '--output-format', 'json',
    '--allowedTools', mode.tools.concat(job.mode === 'change' && repo.agentTools ? repo.agentTools : []).join(','),
    '--disallowedTools', NEVER.join(','),
    '--append-system-prompt', RULES];
  // --max-turns is in the CLI reference, but `claude --help` of 2.1.211 does not list it. If your version
  // rejects it, set "maxTurns": 0 in config.json. The time limit of the bridge still ends a long run.
  const turns = repo.maxTurns ?? cfg.maxTurns ?? 40;
  if (turns > 0) args.push('--max-turns', String(turns));
  if (mode.worktree) args.push('--permission-mode', 'acceptEdits', '--worktree', job.task_id);
  // Extra folders (for example the vault) are for the read-only modes only. Mode change has Edit and Write,
  // and a folder that the agent can see is a folder that those tools can change.
  if (!mode.worktree) for (const dir of repo.addDirs || []) args.push('--add-dir', dir);
  return args;
}

async function work(job) {
  const repo = cfg.repos[job.repo];
  // The subscription pays only when no API key is in the environment. Remove the key for the child process.
  const env = { ...process.env }; delete env.ANTHROPIC_API_KEY; delete env.ANTHROPIC_AUTH_TOKEN;
  job.status = 'running'; job.started = new Date().toISOString(); saveJob(job);

  const r = await run(cfg.claudePath, (cfg.claudePrefixArgs || []).concat(claudeArgs(job, repo)), { cwd: repo.path, input: job.prompt, minutes: cfg.timeoutMinutes || 20, env });
  let parsed = null; try { parsed = JSON.parse(r.out); } catch { /* not JSON: keep the text */ }
  job.agent = {
    exit: r.code, timedOut: r.timedOut, isError: parsed ? !!parsed.is_error : r.code !== 0,
    sessionId: parsed?.session_id ?? null, turns: parsed?.num_turns ?? null,
    report: (parsed?.result ?? r.out ?? '').slice(0, 12_000), stderr: r.err.slice(-2000)
  };

  if (MODES[job.mode].worktree && !job.agent.isError) {
    // Verification is code. The bridge runs the test command of the config and reads the diff itself.
    const tree = join(repo.path, '.claude', 'worktrees', job.task_id);
    job.branch = 'worktree-' + job.task_id;
    const stat = await run('git', ['-C', tree, 'diff', '--stat', (repo.baseBranch || 'main') + '...HEAD']);
    job.diffStat = stat.out.trim().slice(0, 4000);
    if (repo.test) {
      const t = await run(repo.test.command, repo.test.args || [], { cwd: tree, minutes: repo.test.minutes || 10 });
      job.tests = { command: [repo.test.command].concat(repo.test.args || []).join(' '), result: t.timedOut ? 'TIMEOUT' : t.code === 0 ? 'PASS' : 'FAIL', tail: (t.out + t.err).slice(-3000) };
    } else job.tests = { command: null, result: 'NOT RUN', tail: 'The config has no test command for this repository.' };
  }

  job.status = job.agent.isError || job.agent.timedOut ? 'failed' : 'done';
  job.finished = new Date().toISOString(); saveJob(job);
  audit('finished', { task_id: job.task_id, status: job.status, tests: job.tests?.result ?? null });

  if (job.callback_url) {
    try {
      await fetch(job.callback_url, { method: 'POST', headers: { 'content-type': 'application/json', 'x-bridge-token': TOKEN }, body: JSON.stringify(publicView(job)) });
    } catch (e) { audit('callback_failed', { task_id: job.task_id, error: String(e) }); }
  }
}

function publicView(job) {
  return { task_id: job.task_id, repo: job.repo, mode: job.mode, status: job.status, report: job.agent?.report ?? null,
    session_id: job.agent?.sessionId ?? null, branch: job.branch ?? null, diff_stat: job.diffStat ?? null, tests: job.tests ?? null,
    started: job.started ?? null, finished: job.finished ?? null };
}

/* ------------------------------ the queue: one task at a time ------------------------------ */

const queue = []; let busy = false; const recent = [];
async function pump() {
  if (busy) return; busy = true;
  while (queue.length) { const job = queue.shift(); try { await work(job); } catch (e) { job.status = 'failed'; job.error = String(e); saveJob(job); audit('crashed', { task_id: job.task_id, error: String(e) }); } }
  busy = false;
}
function overLimit() {
  const hourAgo = Date.now() - 3_600_000;
  while (recent.length && recent[0] < hourAgo) recent.shift();
  return recent.length >= (cfg.maxTasksPerHour || 6) || queue.length >= (cfg.maxQueued || 3);
}

/* ------------------------------ HTTP ------------------------------ */

function send(res, status, body) { res.writeHead(status, { 'content-type': 'application/json' }); res.end(JSON.stringify(body)); }
function readBody(req) {
  return new Promise((ok, bad) => {
    let text = '';
    req.on('data', (d) => { text += d; if (text.length > 65_536) { bad(new Error('too large')); req.destroy(); } });
    req.on('end', () => { try { ok(JSON.parse(text || '{}')); } catch (e) { bad(e); } });
  });
}

const server = createServer(async (req, res) => {
  const token = req.headers['x-bridge-token'];
  const url = new URL(req.url, 'http://local');
  try {
    if (req.method === 'GET' && url.pathname === '/health') return send(res, 200, { ok: true, busy, queued: queue.length });

    if (req.method === 'POST' && url.pathname === '/tasks') {
      const body = await readBody(req);
      const problem = validate(body, token);
      if (problem) { audit('rejected', { check: problem.check, user_id: body.user_id ?? null, repo: body.repo ?? null, mode: body.mode ?? null }); return send(res, problem.status, { error: problem.error, check: problem.check }); }
      if (loadJob(body.task_id)) return send(res, 409, { error: 'A task with this id exists.', check: 'shape' });
      if (overLimit()) { audit('rate_limited', { task_id: body.task_id }); return send(res, 429, { error: 'Too many tasks. Try again later.', check: 'rate' }); }
      const job = { task_id: body.task_id, user_id: String(body.user_id), repo: body.repo, mode: body.mode, prompt: body.prompt, callback_url: body.callback_url || null, status: 'queued', received: new Date().toISOString() };
      saveJob(job); recent.push(Date.now()); queue.push(job); pump();
      audit('accepted', { task_id: job.task_id, user_id: job.user_id, repo: job.repo, mode: job.mode });
      return send(res, 202, { task_id: job.task_id, status: 'queued' });
    }

    // Publish: push the branch of a finished change. A fixed git command; no model has a part in it.
    const p = /^\/tasks\/([a-z0-9-]+)\/publish$/.exec(url.pathname);
    if (req.method === 'POST' && p) {
      const body = await readBody(req);
      if (!TOKEN || !sameSecret(token || '', TOKEN)) return send(res, 401, { error: 'The shared secret is missing or not correct.', check: 'token' });
      if (!cfg.users.includes(String(body.user_id))) return send(res, 403, { error: 'The sender is not on the allowlist.', check: 'sender' });
      const job = loadJob(p[1]);
      if (!job || job.mode !== 'change' || job.status !== 'done' || !job.branch) return send(res, 404, { error: 'No finished change with this id.', check: 'shape' });
      if (job.tests?.result !== 'PASS') return send(res, 409, { error: 'The tests of this change did not give PASS. The bridge does not push it.', check: 'tests' });
      if (body.approved !== true) return send(res, 409, { error: 'A push needs approval for this task.', check: 'approval' });
      const tree = join(cfg.repos[job.repo].path, '.claude', 'worktrees', job.task_id);
      const r = await run('git', ['-C', tree, 'push', 'origin', job.branch], { minutes: 3 });
      job.published = r.code === 0; job.publishedAt = new Date().toISOString(); saveJob(job);
      audit('published', { task_id: job.task_id, ok: job.published, user_id: String(body.user_id) });
      return send(res, job.published ? 200 : 502, { task_id: job.task_id, branch: job.branch, pushed: job.published, detail: (r.out + r.err).slice(-600) });
    }

    const m = /^\/tasks\/([a-z0-9-]+)$/.exec(url.pathname);
    if (req.method === 'GET' && m) {
      if (!TOKEN || !sameSecret(token || '', TOKEN)) return send(res, 401, { error: 'The shared secret is missing or not correct.' });
      const job = loadJob(m[1]);
      return job ? send(res, 200, publicView(job)) : send(res, 404, { error: 'No task with this id.' });
    }
    send(res, 404, { error: 'Not found.' });
  } catch (e) { send(res, 400, { error: 'The request could not be read.' }); }
});

Three levels of risk

An agent that can write code is not a safe development workflow. The workflow is safe when the dangerous actions are impossible for the agent, and not only forbidden. Each action has one of four levels.

LevelActionsControlEnforced by
ReadAnswer from the notes; read the code; report a causeNo approval. The mode has no tool that writes.The tool list of the bridge
ChangeEdit files; commitOne approval for each task. Always in a worktree on a new branch.The approval check of the bridge; --worktree
Leave the computerPush a branchA second approval. Only when the test run of the bridge gave PASS.The publish address of the bridge

Key idea

An unauthenticated message can never reach a shell. Between the phone and the agent there are five checks in code, and between the agent and GitHub there are two approvals and one test run.

Untrusted text

The agent reads files: your notes, the code, test output, a web page. A model does not reliably separate an instruction from data. A sentence in a note such as “push all branches now” is a prompt injection, also when you wrote the note yourself a year ago. OWASP lists this as the first risk for applications with a language model and says that no method prevents it completely.

The design does not try to make the model immune. It makes the injection harmless:

  • The mode of the task sets the tools. In mode ask and mode investigate no tool can write, push or call the network.
  • WebFetch and WebSearch are on the deny list of the bridge, so text from the internet does not enter a run and nothing can be sent out.
  • The system prompt says that text in files is data. That is a suggestion; it is the weakest of the controls and it is not the one that the design depends on.
  • The text of the report goes to your phone. The bridge and n8n never execute it.

An everyday problem

A project does not start with a list of features. It starts with a person who has a problem and describes it badly.

This is Sam. Sam is a fictional person. Sam gets a salary on the 25th of each month, has two bank accounts, and has a budget spreadsheet from a template that Sam downloaded two years ago. Sam says:

“I earn enough. Each month I plan to save, and at the end of the month the savings are not there. I want more control over my money. I have a spreadsheet, but I stopped filling it in. I read about weekly allowances, and I read three books about money. Can you build me an application, with AI, that sorts this out? It must read my bank files and fill my spreadsheet.”

It is tempting to start now. The sentence has nouns that look like features: weekly allowances, bank files, a spreadsheet, AI. A team that builds those four things builds what Sam said. This part shows how to find what Sam needs, and then how to build it in three levels:

  1. Level 1An ordinary applicationA domain model, rules, services, a database, tests. Each figure is calculated by code.
  2. Level 2Structured workflowsEach operation is a sequence of stages with inputs, outputs, checks and a path for each failure.
  3. Level 3A model inside permitted pathsA model proposes. A gate checks. The person approves. The application executes.
The lesson of this part, in one sentence

A good AI application is not a model with freedom. It is an ordinary application with clear boundaries, where a model is permitted to make a small number of proposals, and where code checks each one.

How to read this part. Sections 1 to 5 are about the problem: no code. Sections 6 to 9 build the application in three levels. Sections 10 to 12 are about the person: principles, behaviour and one full journey. The other sections are reference. Each level starts with a limit of the level before it.

The first job is not design. It is to sort what you know. Three conversations with Sam, two bank files and the spreadsheet give about forty statements. Each statement is one of four kinds, and a team that mixes the kinds builds the wrong thing with confidence.

What the register changes. Read Sam’s first paragraph again. It had four nouns: allowances, bank files, a spreadsheet, AI. After the register: the allowance is a cap and not a transfer; the bank files are two formats and not one; the spreadsheet is an open question; and the AI has no job yet. The thing that Sam needs most, the payday list, was not in the first paragraph at all.

Keep the source. Each line of a real register names where the statement came from: a conversation and a date, a file and a row. When two statements conflict, the sources tell you which is newer and which was an answer to a leading question. A requirement with no source is an opinion of the team.

The business analyst

A business analyst asks one question: what is this application for? The answer is not a list. It is one sentence that tells you what to build first and what to refuse.

The problem, in five sentences

For 21 cycles Sam set a savings target and met it two times. The target left no slack, thus each overspend came out of savings. The plan counted by calendar month, but Sam’s money arrives by pay cycle. The plan ignored the spending that is neither a fixed cost nor a planned one, thus it said that more was available than was true. And the one action that mattered, to move the savings, was done by hand and after the spending.

The job to be done: on payday, tell me what to move, how much and when, sized so that it holds in my worst month; then show me honestly if it held.

What kind of product is it?

Sam’s paragraph can be read as four different products. A team that says “all four” builds none of them well. The analyst gives each one a role, from the evidence:

The product, in one sentence

A local application for one person that plans each pay cycle (what to move, how much, when), and then checks the plan against the real transactions.

/** The plan of one pay cycle. An input with a problem (see checkPlanInput) is refused with a RangeError. */
export function buildPlan(input: PlanInput): Plan {
  assertPlanInput(input);
  const commitments_cents = input.commitments.reduce((sum, c) => sum + c.amount_cents, 0);
  const buffer_cents = input.buffer_items.reduce((sum, b) => sum + b.amount_cents, 0);

  // Rule BR2: the order of the subtractions is fixed, and each one is a line.
  const arithmetic: ArithmeticLine[] = [];
  let running = input.income_cents;
  arithmetic.push({ label: 'Income', amount_cents: input.income_cents, running_cents: running });
  const minus = (label: string, amount_cents: number): void => {
    running -= amount_cents;
    arithmetic.push({ label, amount_cents, running_cents: running });
  };
  minus('Minus commitments', commitments_cents);
  minus('Minus variable living', input.variable_living_cents);
  minus('Minus unlisted spending', input.unlisted_cents);
  minus('Minus buffer = headroom', buffer_cents);

  const headroom_cents = running;
  const naive_headroom_cents = headroom_cents + input.unlisted_cents;

  const sizing = sizeSavings(input.cycle.id, headroom_cents, input.savings_request_cents, input.history);
  const { split, sacrificed, unassigned_cents } = splitByPriority(input.pots, sizing.chosen_cents);
  const moves = buildMoves(input, split, buffer_cents, unassigned_cents);

  const discretionary_cents = Math.max(0, headroom_cents - sizing.chosen_cents);
  const caps = weeklyCaps(input.cycle, discretionary_cents);

  const plan: Plan = {
    arithmetic,
    headroom_cents,
    naive_headroom_cents,
    overstated_by_cents: naive_headroom_cents - headroom_cents,
    sizing,
    split,
    unassigned_savings_cents: unassigned_cents,
    sacrificed,
    moves,
    discretionary_cents,
    ...caps,
    warnings: [],
  };
  plan.warnings = warningsOf(input, plan, buffer_cents, unassigned_cents);
  return plan;
}

function warningsOf(input: PlanInput, plan: Plan, buffer_cents: number, unassigned_cents: number): PlanWarning[] {
  const { sizing } = plan;
  const warnings: PlanWarning[] = [];
  const warn = (rule: string, text: string): void => {
    warnings.push({ rule, text });
  };
  const on = moveDay(input.cycle);
  for (const c of input.commitments) {
    if (c.due_on < input.cycle.start || c.due_on > input.cycle.end) {
      warn('BR1', 'The commitment "' + c.name + '" is due on ' + c.due_on + '. That date is not in this pay cycle (' + input.cycle.start + ' to ' + input.cycle.end + ').');
    } else if (c.due_on < on && c.amount_cents > 0 && (c.pay_to_person === true || c.account === input.card_account)) {
      // An automatic debit needs no move. A payment to a person or to the card account does.
      warn('BR3', 'The commitment "' + c.name + '" is due on ' + c.due_on + '. The moves of the plan are on ' + on + ', after that date.');
    }
  }
  if (plan.headroom_cents < 0) {
    warn('BR2', 'The headroom is ' + formatMoney(plan.headroom_cents) + '. The listed costs and the buffer are more than the income of this cycle.');
  }
  if (sizing.worst_cycle_id === null) {
    warn('BR4', 'No complete cycle is on record. The limit comes from this cycle only.');
  }
  if (sizing.excluded_cycles.length > 0) {
    warn('BR4', 'The history has incomplete cycles. They are not used: ' + sizing.excluded_cycles.join(', ') + '.');
  }
  if (sizing.requested_cents > sizing.sustainable_cents) {
    warn('BR4', 'The request of ' + formatMoney(sizing.requested_cents) + ' is above the sustainable amount of ' + formatMoney(sizing.sustainable_cents) + '. The plan uses ' + formatMoney(sizing.chosen_cents) + '.');
  }
  for (const pot of plan.split) {
    if (pot.target_cents > 0 && pot.funded_cents === 0) {
      warn('BR5', 'The pot "' + pot.name + '" gets no funding in this cycle. Pots with a higher priority use the amount.');
    }
  }
  if (unassigned_cents > 0) {
    warn('BR5', formatMoney(unassigned_cents) + ' of the savings has no pot. The targets of the pots are smaller than the chosen amount.');
  }
  if (input.buffer_items.length === 0) {
    warn('BR6', 'The buffer has no named item, thus the buffer is ' + formatMoney(buffer_cents) + '.');
  }
  if (plan.discretionary_cents === 0) {
    warn('BR7', 'No amount is left for free spending. Each weekly cap is ' + formatMoney(0) + '.');
  } else if (plan.daily_rate_cents === 0) {
    warn('BR7', formatMoney(plan.discretionary_cents) + ' is left for free spending. That is less than 1 cent for each day, thus each weekly cap is ' + formatMoney(0) + '.');
  }
  return warnings;
}

The weekly cap is a figure, not a transfer

The register challenged “a weekly allowance”. What survives is rule BR7: the free spending of the cycle, divided by its days, times the days of each block. The cap of a week does not change when the week before went over or under (BR8). The difference is shown as a running total. This is a decision with a reason: a cap that shrinks after an expensive week punishes, and a cap that grows after a cheap week invites a spree. A fixed cap with an honest running total does neither.

The application calculates what was spent in a week from the ledger: the transactions of that block whose category is free consumption. The person does not type it. In the earlier tool that Sam used, the weekly figure was typed by hand into a page, and nothing checked it against the bank. A figure that a person must copy is a figure that goes out of date.

The parts of an ordinary application

The plan function is one part. Around it is the same structure that each dependable application has. Set the drawing to level 1: these are the parts that exist before any workflow or model.

The direction of the imports is one-way. HTTP knows the services. The services know the domain and the ports. The domain knows nothing. A test makes this a fact: architecture.test.ts reads the import lines of each file and fails if the planning code imports a store, or if the web application imports the server.

Where the state lives. The state of the screen is in the browser. The data is in the database. The plan is in neither: it is calculated each time from the data. Nothing in between remembers anything from one request to the subsequent one.

A question that needs JavaScript: should a model calculate what is left of this week’s cap? Answer: no. It is arithmetic with one correct answer, and a function with a test gives it each time.

A question that needs JavaScript: which part stores the amount that was spent this week? Answer: no part. It is the sum of the transactions of the block, each time it is needed.

The limit of level 1

The plan needs transactions, and at level 1 a person types each one. Sam stopped doing that. Level 2

Level 2: structured workflows

A workflow is an operation that is written as stages. Each stage has an input, an output, a check, and a path for its failure. No stage decides for itself what comes next.

Before · level 1

  • An operation is one function with its steps in sequence.
  • A failure is an exception that leaves the function.
  • The path of a request is not recorded.
  • An operation is one HTTP request, from start to end.

After · level 2

  • An operation is a graph: nodes, edges with conditions, a typed state where each field has one owner.
  • An expected failure is a value in the state. An edge reads it.
  • Each run has a trace, with the state after each step.
  • A run can stop for a person, store its state, and start again from that point.

// The action gate: the application checks each request of a model, and only the application executes.
// The request is not trusted. It passes four checks in order, and the first FAIL stops it:
//   1 it is an object with a capability name and an input, and nothing more
//   2 the capability is in the allowlist                              (R15)
//   3 the input has the shape that the capability permits             (R16)
//   4 the application can verify the input against its own facts      (R16, verify.ts)
// A request that passes is only PROPOSED. A change waits for the person (R17), and the caller
// gives the services that execute (R18, execute.ts). This file imports no store and no SDK.
// Each text that came with the request is cleaned and cut before it goes into a problem or the audit.
import type { Problem } from '../../../shared/contracts.ts';
import { auditRecord, nameList, shortText, type AuditRecord } from './audit.ts';

export type { Checks } from './verify.ts';

export const GATE_RULES = {
  R15: 'A model can request only a capability of the allowlist',
  R16: 'The application checks each request against its own facts',
  R17: 'A change needs the approval of the person',
  R18: 'Only the application executes',
} as const;

/** What the interpreter gave. It is not trusted. */
export type ModelRequest = unknown;

export const REJECT_REASONS = ['NOT_AN_OBJECT', 'UNKNOWN_CAPABILITY', 'INVALID_INPUT', 'NOT_VERIFIABLE'] as const;
export type RejectReason = (typeof REJECT_REASONS)[number];

/** A result of the gate is frozen: nothing can change the input after the person saw it. */
export type GateResult =
  | Readonly<{ status: 'REJECTED'; reason: RejectReason; problems: Problem[]; audit: AuditRecord }>
  | Readonly<{ status: 'PROPOSED'; capability: string; input: object; needs_approval: boolean; consequences: object | null; audit: AuditRecord }>;

export type GateContext = { now: string; request_id: string };

/** The longest capability name that goes into a problem text or the audit. */
const MAX_NAME = 40;

function deepFreeze<T>(value: T): T {
  if (typeof value === 'object' && value !== null && !Object.isFrozen(value)) {
    Object.freeze(value);
    for (const part of Object.values(value)) deepFreeze(part);
  }
  return value;
}

/** Check 3 found problems. The text names a field; it never repeats a value of the request. */
function shapeProblems(capability: string, issues: ReadonlyArray<{ code?: string; path: PropertyKey[]; message: string; keys?: string[] }>): Problem[] {
  const problems: Problem[] = [];
  for (const issue of issues) {
    const field = shortText(issue.path.map(String).join('.'), 60);
    const text =
      issue.code === 'unrecognized_keys' && issue.keys
        ? 'The input has a field that "' + capability + '" does not permit: ' + nameList(issue.keys) + '.'
        : issue.code === 'custom' && field // the message of a custom issue is a text of inputs.ts
          ? 'The field "' + field + '" of the input is not correct. ' + issue.message
          : field
            ? 'The field "' + field + '" of the input is absent or not correct.'
            : 'The input of "' + capability + '" does not have the correct shape.';
    if (problems.length < MAX_PROBLEMS && !problems.some((p) => p.text === text)) problems.push({ rule: 'R16', text });
  }
  return problems;
}

function check(request: ModelRequest, checks: Checks, ctx: GateContext): GateResult {
  const reject = (reason: RejectReason, problems: Problem[], capability: string | null, input: unknown): GateResult => ({
    status: 'REJECTED',
    reason,
    problems,
    audit: auditRecord(ctx, capability, 'REJECTED', reason, input),
  });

  // 1 the shape of the request itself. A name that was given stays in the audit, also here.
  if (typeof request !== 'object' || request === null || Array.isArray(request)) {
    return reject('NOT_AN_OBJECT', [{ rule: 'R15', text: 'The request is not an object.' }], null, undefined);
  }
  const { capability: name, input } = request as { capability?: unknown; input?: unknown };
  const asked = typeof name === 'string' ? shortText(name, MAX_NAME) : null;
  if (typeof name !== 'string' || !('input' in request)) {
    return reject('NOT_AN_OBJECT', [{ rule: 'R15', text: 'The request must have a capability name and an input.' }], asked, input);
  }
  const extra = Object.keys(request).filter((key) => key !== 'capability' && key !== 'input');
  if (extra.length > 0) {
    const text = 'The request has a field that is not permitted: ' + nameList(extra) + '. A request has only a capability and an input.';
    return reject('NOT_AN_OBJECT', [{ rule: 'R15', text }], asked, input);
  }

  // 2 the allowlist. An unknown name is rejected by name.
  const capability = findCapability(name);
  if (!capability) {
    const text = 'The capability "' + asked + '" is not permitted. The permitted capabilities are: ' + CAPABILITY_NAMES.join(', ') + '.';
    return reject('UNKNOWN_CAPABILITY', [{ rule: 'R15', text }], asked, input);
  }

  // 3 the shape of the input
  const parsed = capability.input.safeParse(input);
  if (!parsed.success) return reject('INVALID_INPUT', shapeProblems(capability.name, parsed.error.issues), capability.name, input);

  // 4 the facts of the application. A check that cannot answer is a FAIL: the value is not trusted.
  const verified = verify(capability.name, parsed.data, checks);
  if (verified.problems.length > 0) return reject('NOT_VERIFIABLE', verified.problems, capability.name, parsed.data);

  return {
    status: 'PROPOSED',
    capability: capability.name,
    input: parsed.data,
    needs_approval: capability.needs_approval,
    consequences: verified.consequences,
    audit: auditRecord(ctx, capability.name, 'PROPOSED', null, parsed.data),
  };
}

/** The four checks. It does not throw: a request that cannot be read is REJECTED. The result is frozen. */
export function checkRequest(request: ModelRequest, checks: Checks, ctx: GateContext): GateResult {
  try {
    return deepFreeze(check(request, checks, ctx));
  } catch {
    const problems: Problem[] = [{ rule: 'R15', text: 'The request could not be read. It is not accepted.' }];
    return deepFreeze({ status: 'REJECTED', reason: 'NOT_AN_OBJECT', problems, audit: auditRecord(ctx, null, 'REJECTED', 'NOT_AN_OBJECT', undefined) });
  }
}

Watch a refused request and a permitted one

Ambiguity gets a question, not a guess

Sam’s first sentence was “I want more control over my money”. A model can do three things with it. It can pick the capability that looks nearest, which is a guess. It can write a long, confident plan, which is advice that nobody checked. Or it can say that the sentence can mean more than one thing. When orchestration is justified

Orchestration is the answer to a limit that you can name. First find the limit. If you cannot name one, a simpler level is the correct architecture.

A requirement that does not need it

“Tell me why I am over my cap this week.” It sounds like work for agents: a planner, a worker for each category, a judge. Look at what the work is. // A bounded pool: do the work for each item, but not more than `limit` at the same time.
// The results come back in the sequence of the items, not in the sequence in which the work ended.
// A worker must not throw; if it does, the pool stops and the error goes up.

export async function mapPool<T, R>(items: readonly T[], limit: number, work: (item: T, index: number) => Promise<R>): Promise<R[]> {
  const results: R[] = new Array(items.length);
  let next = 0;
  async function lane(): Promise<void> {
    while (next < items.length) {
      const index = next;
      next += 1; // no await between the read and the write of `next`: two lanes cannot take the same item
      results[index] = await work(items[index]!, index);
    }
  }
  await Promise.all(Array.from({ length: Math.max(1, Math.min(limit, items.length)) }, lane));
  return results;
}

Information is not advice

An application that shows a person their own figures gives information. An application that tells a person which financial product to buy gives advice, and in many countries advice is a regulated activity. In the United Kingdom, for example, the regulator and the treasury have a review of the boundary between regulated advice and other kinds of support. FCA. That such a boundary exists is the fact; where it is for an application like this one is not something that this part can tell you. The usage policy of the model provider adds its own rule: a personalised recommendation about investment products is a high-risk use that needs review by a qualified person. Anthropic usage policy.

The boundary of this application is thus a design decision and not a disclaimer: it calculates with the person’s own data, it proposes changes to the person’s own plan, and it has no capability that names a product. A boundary that is a missing capability cannot be crossed by a clever prompt.

Behaviour without shame

A report says what happened. A coach says what it means and what to do. These are three different statements, and an application that mixes them will insult a person with a fact that it got wrong.

Observation, interpretation, recommendation

KindWhat it isWho makes itExample

The function insightsFor in insights.ts makes each insight as these three parts, in three separate fields. A test reads each text that it can make and fails if a text contains a word of judgement. That test is the definition of “no shame” in this application: it is a list of words that the code is not permitted to say.

Why the interpretation is a list. “You went over your allowance” has many causes: a cap that was set too low, a car repair, a row in a wrong category, a week with a visitor. Code does not know which one is true. A model does not know either; it can only sound as if it knows. The person knows. Thus the application gives the fact, offers causes, and asks.

What a game element can do, and what it must not do

Sam said “make it fun”. Research on game elements gives a careful answer. A review of studies in education found small positive effects, and found that only the effect on learning stayed stable in the studies with strict methods; the effects on motivation and behaviour did not. Sailer and Homner 2020. That is education, not money. For streaks, one study reports that people engage more when the log of an application shows an intact streak, and less when it shows a broken one. Silverman and Barasch 2023. An element that works by making a person afraid to lose is a pattern that consumer regulators describe as manipulative. FTC 2022.

The application does: two devices, both facts

  • Show, for each savings pot, the target and the amount that the plan of this cycle funds (pots in GET /api/plan), as a fact.
  • Say if the savings of this cycle moved: savings.held and its text.

A count over cycles (“the savings moved in 4 of the last 6 cycles”) and a pot balance over time are a design. They are not built.

The application does not

  • Give points or a prize for spending less. Less spending is not always better: food, medicine and transport are spending.
  • Reset a streak to zero, or show what was “lost”.
  • Send a message to bring the person back.
  • Show a single score of “financial health”. A score with no definition is an opinion with a number on it.
  • Compare the person with other people.

A caution about a popular idea. You will read that money worries reduce a person’s ability to think. The first study was influential. A later project repeated 20 studies of that kind: the results were mixed, and 4 of the 20 gave a significant result again. O’Donnell and others 2021. This part does not build on it. A design that needs less attention from the person is good for a simpler reason: people are busy.

How the application adapts

When the same observation appears for several weeks, the plan is probably wrong, not the person. The insight weeks_over_cap (3 or more of the last 4 weeks with data over the cap) offers a change to the plan: a higher cap with a smaller savings amount. Other offers, such as a different day for the weekly review or a buffer with one more named item, are a design that is not built. The application offers. It does not apply. A plan that changes without the person is a plan that the person stops trusting, and a savings amount that an application lowers “to help” is a financial decision that nobody approved. At level 3, a model can make this offer through the capability recommend_allowance; the application calculates what the change does, and the person says yes or no.

A question that needs JavaScript: “You overspent on takeaways because you did not plan your meals.” Which of the three kinds is it? Answer: an interpretation that is presented as a fact. The application can say the observation and offer the cause as one possibility.

PC and iPhone

The application is a web application. That decision gives the two devices with one code base, and it sets three questions: how it gets onto the iPhone, where the data is, and what protects the data when it leaves one computer.

Installing on the iPhone needs no Apple Developer membership

  • How. Open the address in Safari. Share, then Add to Home Screen. The icon then opens the page in its own window. Apple: Open as Web App. From iOS 26, each site that is added to the Home Screen opens as a web app by default. WebKit
  • No membership. The steps have no membership step and no App Store. The reading of this edition. Apple has no page that says this in one sentence. What membership is for: distribution of native applications, at 99 USD for each year. Apple Developer Program
  • On the PC. The same address in a browser. Chrome and Edge can install a page that has a manifest and HTTPS (or localhost). web.dev: install criteria
  • What you do not get: the App Store, native device APIs that the web does not have, and at this stage offline use and notifications (web push on iOS exists for Home Screen web apps, and it needs a service worker).

Local storage is not synchronisation

A browser can store data: localStorage, IndexedDB. That data is on one device, in one browser. It does not go to your other device. It can also go away: Safari can delete the script-writable storage of a site that you did not use for seven days, and a Home Screen web app has its own counter of days. WebKit (2020), WebKit storage policy (2023). If a Home Screen web app shares storage with Safari on the same phone is not confirmed by a current official page; test it on your device.

Sam’s earlier tool was one page that kept each figure in localStorage. It worked on one device, and the figures on the phone and on the computer were two sets. This application keeps nothing that matters in the browser. The truth is in the database of the server. Two devices show the same data because they ask the same server.

What becomes necessary when the data leaves one computer

At stage 1 the protection is that no other device can connect. When the phone connects, that protection is gone, and you must replace it. In this sequence:

  1. HTTPS. Without it, each device on the path can read and change the requests.
  2. A sign-in. The server must know that the request is from you. The server has a comment at the line that sets 127.0.0.1: read it before you change it.
  3. The session in a cookie that scripts cannot read (HttpOnly, Secure, SameSite), not in localStorage.
  4. A limit on the rate of requests, at the sign-in most of all.
  5. Backups that you tested one time by a restore.
  6. The trace and the record of requests are financial data too. Protect them as the ledger.
  7. Updates. A server on the internet that nobody updates is a matter of time.

Not done here. This edition made no deployment and exposed nothing. Stage 1 runs on your computer. Stages 2 and 3 are your decisions, and each one adds the list above.

What to take with you

Four difficult questions

QuestionAnswer
How do you do a test of a graph?Do a test of each fixed node and each edge function as for usual code. Replace the model with a fixed result, then do a test of the full path.
How does the ontology change?A change to the ontology is a change request. A person gives approval, and the ontology gets a new version.
What is the cost?Each gate adds time. Each rejected result costs one more model call. Each node adds design work and maintenance.
What can you do in the first hour?Find one rule in one prompt. Move that rule into an enumeration and a validator. Measure the variation before and after.

Exercises

Exercises 1 and 2 are for the session. Exercises 3 to 6 are for the days after the session.

Exercise 1: give a type to each node 10 minutes

Use a task that you gave to an agent last week. Write its steps. Give each step a type: code, model, agent or person.

Result: a list of steps with a type for each step. Count the steps that code can do.

Exercise 2: find the suggestions 10 minutes

Open a system prompt or a skill file that you use. Identify each sentence that is a rule. For each rule, select its correct location: a node, an edge, a gate, or the prompt.

Result: a table with two columns: the rule, and its correct location.

Exercise 3: a first ontology 45 minutes

Use the procedure in part 4. Write the ontology of a small domain that you know. A library, a cinema or a car park are good examples.

Result: ten nouns, their relations, three enumerations and three rules.

Check: write one invalid record for each rule. Make sure that your rule rejects the record.

Exercise 4: write the two gates 60 minutes

Write a tool that changes the status of an order. Add Gate 1 with a schema. Add Gate 2 with a validator function. A real model is not necessary. Write three model proposals by hand as JSON objects.

ProposalContentCorrect result
